# 03 — Plan d'implémentation

Principes :
- étendre l'existant, sans module concurrent ;
- migrations additives uniquement, sans `migrate:fresh` ;
- chaque lot est livré avec ses tests PHPUnit, et Playwright quand une interface change ;
- la [matrice](02-MATRICE-CONFORMITE.md) est mise à jour à la fin de chaque lot.

Ordre retenu : la sécurité et les règles métier d'abord, car un module incomplet mais sûr vaut mieux qu'un module riche mais contournable. Viennent ensuite le protocole lecteur (commandes, capacités, états), puis l'inventaire et la configuration, enfin les vues et les rapports.

## Hors périmètre logiciel ou soumis à validation matérielle

- **Veille matérielle, luminosité, contraste, redémarrage système, température et disque réels** : ils exigent l'agent local et un pilote matériel (HDMI-CEC, RS-232 ou API du constructeur). Ils seront implémentés côté agent et serveur, puis marqués « implémentés — validation matérielle en attente ».
- **Temps réel par WebSocket ou MQTT** : ce serait une nouvelle dépendance d'infrastructure (Reverb ou un courtier), à soumettre à approbation. En attendant, le rafraîchissement HTTP de la supervision sera réduit à 15 s, et la file de commandes sera relevée à chaque battement de cœur (30 s, paramétrable).
- **Plans d'étage réels** : aucun plan n'est fourni. La vue du bâtiment s'appuiera sur le référentiel (étages, salles, emplacements) et acceptera un plan déposé par étage quand il sera disponible.
